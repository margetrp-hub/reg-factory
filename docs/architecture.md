# 架构与目录约定

本页维护当前owner、状态机和存储边界，部署与测试证据统一见[当前验收](acceptance.md)。SG控制面为Go regd，Python执行平台流程，旧webui面板已退役；不得共同调度同一生产数据目录。

SG 是独立的生产与账号资料管理系统。本机生产、账号导入导出、凭据管理、邮箱池、运行日志和独立 CLI 不需要 Work 节点身份或中央资产密钥。Work 接入负责接受授权任务、传输资产和回传证据；它是系统的一项职责。`/api/health` 表示 SG 服务健康，`/ready` 只表示 Work 接入就绪，不能用后者阻止本机功能。

本机凭据保存的 Go 收尾路径：执行器保存原任务 journal → 固定本次结果 → 发布当前凭据 → 提交任务/账号事实并排队 AT 检查 → 清理本次暂存。重启或 Python 不可用时，Go 直接恢复原 journal，不访问上游、不交换 RT。数据库暂时失败继续原任务重试；当前凭据已变化则保留原资料和失败证据，操作员从原账号重新授权。Work 原任务继续保留其不可变结果，本机任务结案后清理自己的暂存。验收必须覆盖无节点配置的本机入口、journal 落盘后中断、数据库收尾失败恢复及旧结果不得覆盖新凭据。

SG使用同机PostgreSQL保存任务、账号投影、邮箱池和待确认回执。Work派发带身份与版本的资产任务，SDK读取中央当前资料，结果先密封落本机再补传。`unknown`保留证据并核对原结果，明确失败释放本任务，成功结果重传不能重跑外部动作；ACK后结束本机暂存投影。节点通信、日志和资产传输共用SDK合同1，节点仍有独立身份和密钥。

面板显式RT修复按请求号和账号身份串行受理；相同账号的别名不能并发交换RT，其他账号独立执行。中断后未确认成功的本地凭据修复按既有规则失败结案，保留原成功资料；新请求可以重试。AT检查仅写对应版本的健康证据。账号封禁与工作区停用分别映射给主控，不连带撤销已有成品。

## 分层

```text
Go regd 控制面 / 本地 CLI 入口
        |
        v
平台流程与编排器
        |
        v
common/ 共享能力
        |
        v
浏览器、邮箱、代理、验证码与下游服务
```

- 根目录入口负责解析参数和编排，不新增通用实现。
- `common/` 放可被两个及以上流程复用的 Python 模块。
- `tools/` 放人工触发的导出、校验、迁移和补传命令。
- `runtime/` 统一收纳根目录外的日志、状态和临时凭据。
- `schema/` 定义公开能力；`server/` 负责控制面 API、任务与界面，不复制平台业务逻辑。
- 独立 K12 适配器位于 `k12/`，拥有自己的服务、前端、任务和数据目录；`gmail_android/`、`vision_solver/` 等仍属于按需独立模块。

## 文件放置规则

新增代码时按以下顺序判断：

1. 用户直接运行的核心流程才放根目录。
2. 可复用业务能力放 `common/`。
3. 一次性维护命令放 `tools/`。
4. 测试放 `tests/`，不要在根目录创建 `test_*.py`。
5. 运行输出只能写入已登记的数据目录，不要生成新的根目录文件类型。

## 运行数据边界

运行数据可能包含个人信息或凭据，必须与源码分开：

| 类型 | 路径 |
|---|---|
| 邮箱池 | `emails.txt`、`outlook_accounts/`、`_outlook_pool/` |
| 会话与凭据 | `cookies/`、`tokens/`、`sso_output/` |
| 日志 | `runtime/logs/`、`tri_register_logs/` |
| 本地状态 | `runtime/state/` |
| 临时凭据 | `runtime/secrets/` |
| 截图与录屏 | `screenshots*/`、`recordings/` |
| 解锁结果 | `unlock_results/` |

这些路径必须保留在 `.gitignore`。目录需要进入仓库时只提交 `.gitkeep`，不能提交样本凭据。

## 控制面能力与配置

### 中央资产任务的 Go 执行宿主

Core 保存账号与业务事实，Work 签名派发，SG 的 Go runner 领取并读取指定版本的中央资料；平台登录授权仍由受控 Python 执行器完成。Go 负责执行意图、加密结果、回库、回执验证和本地结案，Python 不再负责 Work 通信与补传。

状态机：queued → running → claim/read → 持久意图 → 平台执行 → 密封原结果 → waiting_asset → 中央确认 → 本地事务结案 → ACK 清理。执行前失败可明确 failed；持久意图后中断且没有原结果为 unknown，保留证据并交 Work 核对/关闭。已有结果只补传，不重复执行；丢响应先查原回执。停止/超时中止正在执行的动作，仍保存结果或 unknown；关闭浏览器不取消任务。重启恢复、管理员原任务补传和后台重试共用同一恢复入口，单任务互斥、有界并发，其他任务不被阻塞。旧 Python Fernet 意图及结果继续原位读取，确认本地终态后才清理。

本轮验收清单：真实签名接单到终态；Python 不可用时原结果补传和 ACK；丢响应/错回执恢复；执行中停止和重启 unknown；未执行取消；旧 Python 工件双向兼容；原任务身份、日志及中央凭据版本保持一致。逐项实跑结果记录在当前验收页，不以实现存在替代验收。

### 周期巡检读取当前账号库

周期巡检默认关闭，启动服务不立即首扫。显式开启后等待配置周期，再从当前去重账号库建立持久检查批次；ChatGPT 复用手动 AT 检查、最新凭据解析、逐项记录和原运行页，不再扫描旧 tokens 目录。来源文件和历史任务不重复计为账号，正在刷新或检查的账号不重复派发；其他平台保留原扫描能力。

状态机：关闭 → 开启后等待 → 批次 queued → running → 检查完成 succeeded、检查未确认 unknown 或停止 stopped/interrupted。完成仅代表检查结束，逐项 ok、needs_refresh 和异常分别计数；空账号库不创建“成功检查0个”的任务。未知或停止保留已检查与未执行项，操作者在原运行页重测未确认项，不覆盖原记录。巡检只测试 AT，不自动交换 RT 或重新授权，不修改归属和生产事实。

配置运行时重读，关闭后停止新排期；尚未执行的周期 AT 项停止，已在途只读请求收尾。手动检查和凭据更新后自动 AT 核验独立运行。重复调度或服务重启不得在原批仍运行时另排同平台批次；已完成批次的创建时间用于周期去重。启用或改变周期从当前时刻重新计时，不补跑停用期间的轮次。自动批次覆盖当时全部当前账号，继续使用单worker和逐项间隔；手动单批100项限制不变。

### 凭据提交与执行隔离

账号页按目的只提供“检查可用性”和“更新凭据”；单个、批量、来源详情及失败恢复共用更新弹窗。更新前显式选择 RT 刷新或登录重新授权，首次生成凭据选择后者。有密码和2FA的 ChatGPT 重新授权使用协议，其余资料使用原浏览器/邮箱能力；执行方式在运行日志中记录。RT 操作不悄悄切换登录，旧 RT 的交换结果未确认时明确要求重新授权。

提交状态机：选择方式 → 逐项提交 → 已受理或提交未确认。已受理项保留原任务链接，批量重试只处理未受理项；丢响应先按原 request_id 找回原任务，不因切换方式重发另一种动作。关闭弹窗不取消已受理任务，处理记录统一分为“可用性检查”和“凭据更新”。任务执行、原结果恢复、凭据发布和后续 AT 核验继续由下述原 owner 负责，不将受理显示为更新成功。

真实入口为账号页的显式 RT 刷新或重新授权，以及 Work 签名授权任务。Python 拥有上游执行及当前凭据文件，Go 拥有任务、账号投影和签名回执；Core 的归属和业务账务不在 SG 修改。

状态机：queued → running → 上游结果持久保存 → 当前凭据发布 → 任务及账号投影同事务 succeeded。上游明确拒绝或没有可确认结果为 failed，提供重新授权；保存后的中断先恢复本次原结果，不能重新请求 RT。凭据已被后续操作更新时拒绝覆盖，失败记录保留原因。数据库短暂不可用时原任务显示收尾重试并自动继续，其他账号仍可执行；重启先处理原任务保存的结果，再处置无结果的中断任务。人工处理通过原账号资料修正、重新授权及 Work 原任务恢复入口完成。

任务、日志、账号列表及统计使用独立只读连接，读取不占用写入连接。进程状态锁不包住数据库操作；发起和停止使用独立顺序锁，服务停止等待已启动任务收尾。IC收码保留独立索引及连接池。SG使用本机PostgreSQL，日志持久化不经过异步缓冲；不与Aishop Core共用业务库，生产进程不回退旧SQLite。

运行页显示实际 RT 刷新或重新登录授权、当前保存阶段、收尾重试次数和终态反馈。执行方式从原任务阶段记录读取，不因大量日志或收尾重试丢失。AT 测试保持只读；任务结束后日志区域不再把旧阶段显示成当前执行状态。失败可以从原运行页重新授权，已领取账号仍交由 Core 授权。

采用“新增、保留、整合”：新增缺失的处理路径，保留全部已有能力、模式和参数，整合重复定义与执行反馈。页面合并不能把原有操作变成仅可查看或跳转；未就绪能力仍需说明真实配置条件，不从目录消失。

`schema/scripts.py` 是 CLI、Go API、前端导航、配置模式及编辑器的唯一公开目录。`server/tools/export_schema.py` 生成任务 schema、配置 schema 与前端导航元数据，禁止三处手填任务 ID。生产中心先选业务，再在同一表单区域切换执行模式；不同模式保留各自输入，原脚本、参数和请求身份不重命名。账号与平台概览仍可独立进入，六个平台为 Claude、ChatGPT、Grok、Outlook、Kiro、GitHub；组合流程同时出现在关联平台，导出与辅助工具保留。

读取模式目录只在进入/主动刷新时执行，生产概览轮询读取一次全局任务统计及账号投影，不按平台重复请求。执行入口的状态为草稿 → 提交中 → 原请求queued/running → 成功、明确失败、停止或待核对；模式切换不清除草稿，未知提交先核对原request_id。运行和实时SSE日志在独立运行页读取，关闭发起页面不取消已经受理的任务。AT测试不交换RT，RT刷新不暗中重新登录；密码＋2FA协议授权、浏览器/邮箱授权沿用原凭据更新入口及处理记录，不能伪装成注册或AT测试。

公共配置集中在配置中心，由同一设置文件保存。模式关联仅决定哪些字段一起显示：浏览器/代理/邮箱使用真实运行选择字段，按任务选择的短信以及可并存的图形验证工具只选择配置视图，不造全局开关。未选模式、未知自定义键及全部原值保留；保存回读/失败/未知的安全动作见[配置说明](configuration.md)。自动巡检默认关闭，本次页面整理不写入启用值，也不增加自动修复。

| 责任 | 唯一实现 | 原有操作如何保留 |
| --- | --- | --- |
| 任务与模式 | schema + runner | 每个任务的全部参数可搜索，协议/浏览器/邮箱来源等模式显式显示 |
| 系统、物料、节点配置 | settings + ConfigEditor | 同一文件、同一保存契约；不同页面仅筛选用途，未知自定义键保留 |
| 任务执行与证据 | runner + store | queued/running/succeeded/failed/stopped 与日志、原任务定位一致 |
| Work 签名执行 | nodeserver | 外部成功、失败、unknown 与回执保留；节点不结算 Core 业务账务 |
| 平台账号 | accounts API + 平台列表 | 全量计数、分页、单项/批量核验；已领取账号修复仍遵守业务 owner |
| IC 源、邮箱池、独立工具 | 原专属 API/页面 | 保留源管理、索引、池记录及辅助工具，不将其复制为另一套配置 |

### 导入与凭据修复

导入资料后，从账号页显式发起RT刷新或重新授权，原运行页查看保存阶段、结果和安全恢复。凭据完整保存后自动排队AT检查；AT不调用RT。失败保留最后成功凭据，可能消耗RT且没有成功工件时重新授权，不用新任务重复交换旧RT。已交付账号修复继续由Core授权。

配置保存使用原文件；新worker读最新文件，显式部署环境优先。Core订阅付款代理与SG生产出口分别维护，不互相覆盖。接口和重试身份见[API](api.md)。

### SG 到生产中心账号库

生产入口为Core授权需求 → Work原执行 → SG选未使用账号 → 子节点核验、加队、授权和回传。AT通过的 `ok` 与 `normal/active` 等价；未知、失效、停用、资料不完整、已领取或已加队均排除。Core不代节点测活。`produce`执行新生产，`existing_result`沿原授权恢复已保存结果，不能自动换账号或重复生产。

入口为导入原账号后通过更新凭据选择登录重新授权，SG 保存凭据和任务事实，Core 只经 Work 读取签名目录，不导入凭据、不领取或增加库存。状态机：完整凭据保存成功 → 持久排队只读 AT 检查 → AT 通过且未领取、未加队、无生产历史时 available；AT 拒绝为 pending 并提供显式 RT 刷新/重新授权；明确停用为 invalid；网络结果未知为 pending，保留检查记录并可重测。未结案的保存恢复、历史unknown及Work外部未知仍由原任务处理，不能被AT成功解锁；本地凭据任务无成功工件的失败按下文释放占用。已领取/生产账号为 used，永不自动回到可用库。

验收清单：目录/引用证明使用同一状态且先筛选后计数分页；刷新成功与后续 AT 检查同事务保存；AT 结果不得覆盖核验期间变化的凭据版本；成功与未知重测从原入口核验；发布后回读约定样本及生产中心真实页面。未完成的验收不作为运行时业务开关。

### 账号计数与原始来源

账号页按平台及规范化身份合并展示；同一个账号的导入资料、凭据文件和生产结果不重复计为多个账号。没有身份的记录保持独立，跨平台不合并。原始来源、凭据版本、托管绑定、任务和修复引用均不重写；展示行必须能展开全部原始来源并通过原引用查看详情。

读取状态机为首次读取/空列表/已加载 → 刷新中 → 更新成功或保留旧结果并可重试。总数与分页采用同一投影；可用、异常、待核验、已使用、处理中为互斥计数，总和必须等于身份数，来源记录数单列。任何同身份已领取/生产事实优先显示已使用；未结案刷新优先于健康状态。聚合读取不解除锁，不写业务或凭据。凭据修复、签名引用和回执仍按全部原始 ref 查找，不能从去重后的显示列表反查，否则旧订单会失去修复来源。

验收覆盖正常去重、空身份/跨平台边界、领取及未知刷新保留、旧来源的签名引用与失败恢复，以及页面重新读取。只有计数通过而原引用失联不算完成。

来源保留用于避免计数调整破坏原订单修复，不代表旧文件永久保留。后续资料清理应区分账号当前有效凭据、旧来源编号及必要执行证据；先确保旧编号仍能解析到正确账号与版本，再清理没有有效引用的重复文件，不能把删除文件等同于删除账号或历史业务关系。

### 状态与恢复

- 页面按操作对象分离：`accounts/` 仅列账号、筛选、选择和发起；`checks/` 列持久批次与刷新历史；发起后及查看记录均进入独立 `runs/?batch=…` / `runs/?mode=refresh&task=…`，只显示本次进度、逐条结果、日志与恢复操作，返回保留筛选/分页。账号与历史页不内嵌运行区。旧检查明细链接保留原记录跳转到运行页。记录由服务端保存，关页或刷新浏览器不取消已受理工作。
- AT 检查：同一 request_id 原子建立任务与逐条记录 → queued → running → succeeded（检查结束，不代表每个 AT 有效）。单条 401/缺 AT 为 needs_refresh，不推断 RT、账号或订阅失效；网络/TLS 有界重试耗尽为 unknown，停止该批后续检查并保留未执行项。操作员可只重测未知/未执行项，新批关联原批，原结果不覆盖。
- 检查证据位于现有任务表及 `credential_check_items`，不存 Token，也不复制账号、库存或业务权威。单批最多 100 项，排队上限 20 批，单 worker 串行处理；AT 每项总时限 30 秒、网络/TLS/5xx 最多 3 次，429/401 不重试。其他平台原报告任务最多等待 90 秒，未确认则保留关联任务并停止该批后续项。
- 停止批次：queued → stopped；running → stopping → 当前只读请求收尾后 stopped。服务重启 → interrupted，原结果保留，未确认项可重测。API 检查执行器独立拥有此任务，普通 Python runner 不领取它。
- RT 刷新始终是独立显式操作，进入原刷新任务追踪；检查绝不调用 RT。其他平台既有报告核对能力保留并明确标记为历史报告，不伪称实时 AT 测试。无凭据内容写入检查记录。
- RT 刷新生命周期：按账号串行受理 → queued → running → 本次完整凭据和任务结案一致后 succeeded；没有可确认成功结果的已结束任务为 failed。已保存结果优先本地恢复，数据库结案短暂失败自动重试；无法恢复则保留失败证据并允许重新授权，不重复交换可能已消耗的 RT。历史 unknown 仍可由原任务核对或人工结案，不再新建无限期占用账号的未知任务。

- 发起任务：编辑 → 提交 → 受理 queued → running → succeeded/failed/stopped。丢失提交响应保留 request_id，先核对原任务；确认未受理才以同一 ID 重发。同请求重放不重复启动。
- 外部动作：明确未产生副作用的失败可回传 failed；副作用未知保持 unknown、原任务和证据，交由原任务核对/人工恢复，不通过新建任务推断成功或失败。
- 账号刷新失败：Python 内部保留稳定的小写原因，只有带 `account.failure.v1` 标记、stdout 结构化事件中的允许原因才能进入签名回执；节点边界统一为 `WORK_ACCOUNT_` 加大写错误码，供 Core 映射安全说明。历史无标记事件仍返回 `WORK_ACCOUNT_REFRESH_FAILED`，保持原结果摘要。ChatGPT 凭据任务的 exit75 先恢复原保存结果，不能确认则失败并释放占用，下次改用重新授权。原始上游响应与登录资料不进入公开回执。
- 配置：读取 → 编辑 → 保存 → 回读确认；失败保留草稿，结果未知先回读。文件未设置与默认值分开显示，默认值不自动写入。
- 新 Python worker 启动时读取最新文件；已运行 worker 保留启动快照。真正部署环境变量仍优先。节点身份、签名密钥和 Go 进程级配置需重启，保存成功不等于已经生效。
- 列表首次读取、空结果、刷新中、刷新失败分别显示；失败保留旧记录及重试。轮询串行、有界、离页取消；统计在完整集合上完成后分页。

## 邮箱池管理

管理员在同一邮箱池入口管理 IC 地址、Outlook 和通用邮箱；后两者继续使用原账号存储，不复制凭据。IC 地址独立于收信存在，来源配置、收信取码、同步运行、邮箱设置分别为独立页面；新增、编辑、导入和清理在本页浮层完成。公开取码保留 Turnstile，管理接口使用面板认证。

- 地址：导入/收信发现 → active；管理员可暂停 paused 或阻止 blocked，再恢复 active。暂停/阻止在所有取码入口生效，收信证据仍保留。清理邮件不删除地址和手工状态。
- 来源：保存 → starting → running；连接错误显示具体错误并自动有界间隔重连。修改连接配置会先停止旧连接再启动新连接；停用后停止收信，重新启用可恢复。已有收信的账号、服务器、文件夹属于历史身份，替换时新建来源。
- 来源连接快照在消息和游标落库的同一写锁内核对；账号、服务器、端口或文件夹被替换后，旧连接不能写入新来源的邮件、游标或错误，原同步为 interrupted，新连接继续自动收信。
- 手工同步：同一 request_id 幂等受理 → pending → running → completed/failed；配置变更或进程停止为 interrupted，来源停用/删除的未执行请求为 cancelled。运行页保留来源、请求编号、开始/结束时间、新增邮件数及失败原因。丢响应先查询原编号，再以相同编号重发；终态重试使用新编号且不覆盖原记录。同步只读取上游邮件，重复执行按来源与 UID 去重，不重复产生邮件或统计。
- 自动收信继续由来源运行器负责，不要求管理员反复点击同步。连接初始时限30秒，每轮索引时限60秒；失败后至少间隔5秒重连。同步结果未确认时保留已写入证据，管理员可以在运行页再次同步。
- 消息、精确收件地址索引及旧计数在同一事务写入；跨来源相同 UID 可并存。历史别名状态和邮件只在结构升级时回填地址池，正常列表不再扫描所有邮件。IC 是 SG 原有的独立索引存储，不改变 Aishop Next 的 PostgreSQL 业务事实边界。
- 历史地址先统一大小写及首尾空格再合并状态；保留最新的手工状态和证据，同一时间优先保留限制较严格的状态，避免升级后暂停或阻止意外失效。清理仅通过 POST 执行，保留天数由服务端校验为 1–3650 天，清理不删除地址与手工状态。

## 账号当前凭据

### 生产与旧凭据任务的现役存储修复

生产链的唯一在线数据库必须与Go当前连接相同：签名物料登记 → 幂等接单queued → 原账号占用 → 邀请前持久标记 → 授权前持久标记 → 加密原结果 → Go成品登记和回执。邀请或授权结果未确认保留unknown及原账号，自动核对/退避；达到有界次数转waiting_user，管理员可继续原任务或终止；停止先持久围栏，再核对none/occupied，已发结果只恢复原结果。数据库不可达在外部动作前失败，不转向旧SQLite快照。PG事务必须保持账号选择互斥、停止与接单排序及任务/生产进度原子更新，网络操作不持有数据库事务。

旧凭据任务的防重由Go使用当前任务库负责：原任务仍运行则拒绝第二个执行；同账号之前的RT结果不确定则只允许明确的登录重新授权；新成功凭据结案后才解除这项保护。只读历史查询失败时不执行平台操作。保存成功但未结案的结果仍走原任务恢复，其他账号独立推进，启动前停止不误判为已消费RT。Python保留账号文件锁和原结果恢复，不再以旧regd.db决定是否重发RT。

本轮验收需经过真实签名接单入口和PG事务，覆盖正常成品、邀请丢响应、停止/恢复、接单前失败与同账号新RT任务防重；独立隔离上游，不能把这些测试当作真实账号生产成功。

### 401、空间停用与封禁状态

状态与责任：Core 保有中央资产事实，Work 派单及接收原结果，SG 执行并保留证据。只读 AT 核验成功为 alive；普通 401 为 needs_refresh，不证明账号封禁或 RT 失效。结构化 account_deactivated/account_banned 为 banned，workspace_deactivated/deactivated_workspace 为 workspace_deactivated；它们独立于任务成功/失败，不自动刷新或换账号。管理员可查看原任务及状态，后续只读复测可确认上游恢复。

显式修复：领取当前版本 → 验证唯一账号/完整凭据位置 → 执行一次 RT 或授权 → 保存完整结果 → Work 回库确认 → 本地结案/ACK。明确拒绝为 failed 且保留状态与最后成功凭据；网络或交换结果不确定为 unknown，保留原任务工件并由原任务补传/人工结案，不能重复消耗旧 RT。嵌套 accounts/credentials 格式必须原位整套更新，多账号资料在执行前拒绝。失败原因只采用结构化白名单，正文或 HTTP 状态不作为封禁证据。

验收包含单账号嵌套凭据回库、普通 401 与明确两状态的区分、失败不覆盖凭据、断网补传不重复执行、旧回执摘要不变，以及本地状态/筛选和中央投影一致。

### 内置邮箱池的执行边界

注册与授权共用 IC 邮箱池的地址、收件来源和暂停状态，不复制 IMAP 登录资料。注册选择 `icmail` 时只取已绑定启用来源的可用地址，在现有跨进程邮箱占用锁下登记；授权按原账号邮箱精确取信，不分配新地址。执行进程通过本机已认证接口读取，不直接打开邮箱数据库。

状态流：选择来源 → 校验地址/来源 → 注册登记占用或授权绑定原地址 → 等待本次新邮件 → 提交验证码 → 原注册/凭据任务保存成功结果。地址不可用、读信失败或等待超时返回原任务失败及原因；重试仍使用原任务入口，已尝试注册的地址不自动重新分配。若注册后未拿到凭据，可对日志中的原邮箱重新授权。停止或中断保留原任务与邮箱使用记录，管理员可在邮箱池重配来源后按原邮箱恢复；不因失败删除邮箱或历史邮件。RT 刷新不读取邮箱，也不变更为登录授权。

取码从发起前记录的消息编号与本次发送时间开始，拒绝其它收件人、其它来源、旧验证码与重复验证码。等待有上限，正常路径自动继续，无需手工确认；邮箱登录由管理员在原收件来源页面维护。

账号按平台、规范化邮箱归拢，上游用户身份不得串用。已确认相同用户转入新工作区时，当前工作区随成功凭据整套更新，旧交付的业务权限仍由 Core 校验。原来源编号和任务结果保留引用意义；执行、修复、AT 测试和默认下载统一解析该身份最近一次成功保存的完整凭据，不再由旧文件名决定版本。账号复用继续更新当前资料，不新增账号计数。

状态机：queued → running → 上游成功且当前凭据原子保存 → succeeded；明确拒绝、超时、交换后中断、缺少完整成功工件等未确认成功的结束任务均为 failed，记录原因、释放账号占用，保留上一次成功凭据。新任务可以重新发起；RT 交换响应丢失后的新尝试明确要求选择登录重新授权，不重复交换可能已消耗的 RT，也不暗中切换方式。相同账号的来源编号共用执行互斥，写回前核对源版本，过时结果不能覆盖新结果。`credential_updated_at` 只表示成功保存时间，扫描、失败和 AT 测试不推进它；历史无可靠时间时不编造时间。

验收：旧来源与新来源读取相同当前凭据；修复成功后旧来源下载和签名回传均为新值；明确失败保留旧值及时间并可重试；并发/过时回写受保护；不同工作区隔离；原任务结果和 Core 授权范围不被改写；账号不因资料来源增加而重复计数。

成功任务在发布当前凭据前保存本次接收工件，原回执摘要不会随账号下次复用而变化。缺少本次成功工件时回传失败，不能把账号旧资料冒充新任务结果。运行配置与当前凭据分开，AT 测试不写凭据保存时间。

`tools/compact_credentials.py` 默认只预览；停止凭据执行后使用 `--apply`，将重复 OAuth 和旧 Free 文件收敛为引用和身份元数据，保留登录材料与原任务记录。写入当前资料后逐一验证所有旧引用再移除过期结果文件；执行中的刷新摘要和最近十分钟的接收材料保留。已结束任务不继续保留旧凭据副本，旧版本摘要不能再用于常规下载，调用方收到“凭据已更新”并下载当前版本。

读取列表、来源详情和下载只计算摘要，不生成结果副本。任务启动时才固定恢复输入，成功/失败或人工结案后释放该临时输入；原任务保留摘要与时间。Python 写回恢复材料保留到 Go 任务结案确认，再自动清理；清理失败保留私有材料和运维提示，不撤销已确认成功的任务。Work 尚需核验的本次任务回执与当前账号资料分开，账号复用不能改写旧回执。新 AT 测试取当前 AT，新刷新取当前 RT，新生产任务取当前资料；查询旧任务不读取当前凭据来重建旧结果。

## 任务 schema 约定

新增任务时：

- `file` 指向仓库内真实入口。
- 参数 flag、类型和默认值必须与 CLI parser 一致。
- 所有参数都必须进入 schema；模式与来源直接可见，低频参数可折叠但必须可搜索、可编辑。
- 为 schema 和命令构建补充测试。
